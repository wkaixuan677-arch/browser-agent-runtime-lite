# 面试讲解材料

## 30 秒版本

这个项目不是普通网页自动化，而是一个证据门控的 Browser Agent 最小运行时。它把“进程结束”和“用户目标完成”分开：策略负责决策，验证器根据 Task Contract 和网页证据判定成功；工具失败、证据不足或假完成会进入有预算的恢复流程。仓库使用 Playwright 本地页面做确定性演示，能够复现正常完成、恢复成功和明确阻断三类轨迹。

## 2 分钟版本

1. **问题**：Browser Agent 常出现零步终止、重复点击、浏览器动作结束但没有最终回答，以及遇到阻断仍声称成功。
2. **设计**：我把运行过程拆成 Plan、Act、Verify、Recover、Finalize，并用 Task Contract 固定目标、成功条件和预算。
3. **关键点**：Policy 无权直接完成任务；只有 Verifier 收到 URL/可见文本等证据后才能放行。重复失败动作通过动作指纹限制，恢复次数全局有界。
4. **Memory**：经验带生命周期，只有经过验证并晋升为 `promoted` 的记录才会检索并注入 Policy 上下文，避免一次错误经验污染后续任务。
5. **安全边界**：跨域导航在网络请求发出前就由 allowlist 拦截，而不是访问后再补判。
6. **验证**：公开仓库提供完全本地、无需模型密钥的场景和自动测试，因此面试官可以直接复现机制。

## 高频追问

### 为什么不让模型自己判断完成？

模型可能在页面加载后把“看到页面”误判成“完成用户目标”。把完成权交给独立 Verifier，可以要求每条成功条件都绑定观察证据。

### 为什么要限制恢复次数？

无限重试会造成循环、Token 浪费和不可预测副作用。有界恢复让失败可解释，并保证 Agent 最终进入 COMPLETED、PARTIAL 或 BLOCKED。

### Memory 为什么需要生命周期？

失败总结不一定正确。Candidate 直接注入可能产生负迁移，因此只有完成验证和晋升的经验才可自动使用。

### 这个公开仓库证明了什么？

它证明运行时控制、证据验证、恢复预算和 Memory 门控能够被独立复现；它不证明真实网页或多模型上的生产性能。

## 演示顺序

1. 运行 `npm run demo`；
2. 展示 happy-path；
3. 展示一次失败后恢复的 bounded-recovery；
4. 展示 explicit-blocked 安全终止；
5. 打开轨迹解释为什么这些状态可审计。
